# Независимый AAA-аудит «Дурак Онлайн 3D»

**Дата проверки:** 16 августа 2026  
**Формат:** второй аудит, выполненный с нуля  
**Основание:** код, сетевые пробы, интеграционные тесты, headless-визуальный прогон и ручной мобильный прогон  
**Важно:** предыдущий `AAA_ROADMAP.md` не использовался как источник выводов

## 1. Короткий ответ

Проект уже имеет узнаваемое визуальное направление и работающий вертикальный срез, но до production-качества карточной live-service игры ему не хватает не «ещё более дорогой графики», а четырёх фундаментальных слоёв:

1. доверенной идентификации, платежей и экономики;
2. строгой серверной модели правил и комнаты;
3. устойчивого клиента с корректным fallback без WebGL;
4. premium-feel карточного хода: выбор легальных карт, адресный отбой, анимационные дельты, звук и восстановление матча.

Текущее состояние по независимой шкале — **34/100**. Это не оценка идеи или старания; это доля закрытых требований выпускаемого multiplayer-продукта.

«AAA+++» не является отраслевым стандартом. Практическая продуктовая цель:

> Самая цельная premium-версия дурака в VK: первый матч за несколько касаний, безошибочные правила, 55–60 FPS на среднем Android, восстановление после сворачивания приложения, неподделываемые фишки и карты, которые приятно разыгрывать сотни раз.

## 4. Что уже действительно хорошо

### 4.1 Игра запускается и доходит до хода

Quick match создаёт комнату, добавляет трёх ботов, раздаёт по шесть карт, скрывает чужие руки и отдаёт состояние через Socket.IO. Это не статичный mock.

### 4.2 Сервер хранит основные правила

`DurakGame` валидирует карту в руке, старшинство масти, козырь, лимит карт, перевод и добор. Клиент не может просто заявить «я победил».

### 4.3 Визуальное направление уже найдено

Комбинация тёмного дерева, зелёного сукна, тёплой люстры и золотых акцентов узнаваема. Полный редизайн не нужен.

В репозитории действительно присутствуют и отдаются с HTTP 200:

- `casino_bg_portrait.jpg`;
- `casino_room_pano.jpg`;
- `felt_emerald_pure.jpg`;
- `mahogany_rim.jpg`;
- две JPG-рубашки;
- отдельные изображения короля, дамы, валета и туза;
- `atlas_court_sheet.jpg`;
- `oct_table_master.jpg`.

Вывод «графические файлы отсутствуют» неверен.

### 4.4 Мобильная иерархия понятна

В лобби легко найти профиль, валюты и две главные CTA. В матче видны козырь, таймер, роль и четыре действия. Стиль HUD в целом последователен.

## 5. Release blockers

Следующие проблемы запрещают запуск экономики и публичное продвижение, даже если графика станет идеальной.

### P0-1. Сервер доверяет identity клиента

`server/server.js`, событие `auth`, принимает `playerData.id`, имя, аватар, фишки и активные скины без доказательства VK-подписи.

Последствия:

- захват чужого профиля по известному VK id;
- подмена имени и аватара;
- XSS через строки, которые позже вставляются через `innerHTML`;
- невозможность честного рейтинга и бана.

Нужно:

- проверять launch params VK и подпись на сервере;
- создавать собственную server session;
- больше не принимать баланс/инвентарь из сокета;
- экранировать user-generated content и перестать собирать его HTML-шаблонами.

### P0-2. Платёжный endpoint является командой «начислить деньги»

`POST /api/vkpay/order` не проверяет:

- подпись VK;
- существование платежа;
- цену SKU;
- `orderId` на повтор;
- знак и верхний предел `amount`;
- владельца заказа.

Клиент дополнительно сам выполняет:

```js
this.userEconomy.chips += pack.chips;
```

Нужно заменить endpoint на идемпотентный payment callback: сервер получает SKU и подтверждение провайдера, сам находит фиксированную награду и пишет ledger-транзакцию.

### P0-3. Экономика исчезает при рестарте

`EconomyService` хранит пользователей в `Map`. Скины, daily, победы и валюта не переживают новый процесс.

Нужно минимум:

- Postgres: `users`, `wallet_ledger`, `inventory`, `matches`, `payment_orders`;
- транзакционное списание ставки;
- уникальные idempotency keys;
- аудит изменения валюты.

### P0-4. Комнаты и действия недостаточно авторизованы

Подтверждён неправильный первый ход: `attack()` не проверяет, что пустой стол открывает `currentAttacker`.

Дополнительно из обработчиков видно:

- `addBot` не требует host;
- `startGame` разрешён любому при `players.length >= 2`;
- игру можно стартовать повторно и перераздать карты;
- `joinRoom` не запрещает вход в активную игру;
- после старта можно добавить игрока/бота с пустой рукой;
- игровые события получают произвольный `roomId`, но не проверяют membership сокета;
- reaction/item можно отправлять в чужую комнату;
- payload не имеет schema validation и rate limit.

Нужен единый guard для каждого события: authenticated → member of room → permitted role → permitted phase → valid schema → rate limit.

### P0-5. Нет восстановления матча

Disconnect превращает игрока в бота, затем удаляет mapping. Обратного протокола «вернуться на своё место» нет. Для VK это критично: WebView сворачивается при звонке, переходе в Pay или системном диалоге.

Нужно:

- opaque reconnect token;
- grace period;
- сохранение seat/hand на сервере;
- snapshot + monotonically increasing revision;
- повторное присоединение без новой раздачи;
- понятный UI «соединение восстанавливается».

## 6. Корректность игрового движка

### Что покрыто

- структура раздачи;
- приватность чужих рук;
- базовый attack/defend/take/pass;
- таймер без падения процесса.

### Что не покрыто

Тесты не доказывают корректность партии. `test_game_flow.js` иногда считает успехом отправку события без проверки результата. `test_turn_timer.js` всегда завершает процесс кодом 0 даже в `catch`.

Нужна матрица unit/property tests:

- только атакующий открывает пустой стол;
- подкидывающие действуют только после открытия;
- нельзя действовать в неверной фазе;
- первый раунд и лимит защитника;
- перевод цепочкой между 2–6 игроками;
- добор строго по часовой стрелке;
- выход нескольких игроков в одном раунде;
- пустая колода и последний козырь;
- disconnect/reconnect на каждой фазе;
- повторное событие и событие со старой revision;
- инвариант: каждая карта находится ровно в одном месте.

Для колоды полезен property test:

```text
hands + deck + table + discard = deckSize
all card ids are unique
```

### Боты

Бот использует младшую некозырную и первый допустимый отбой. Это годится для smoke test, но не для повторной игры.

Перед «умным AI» нужно устранить гонки планировщика: `handleBotTurns` создаёт независимые `setTimeout` при многих обновлениях и не хранит один pending job на комнату.

## 7. Графика: нужна ли новая

### Полный редизайн — нет

Существующая quiet-luxury арт-дирекция подходит продукту. Новый визуальный мир отложит выпуск и не исправит core.

### Production-проход по графике — да

Причина не в количестве пикселей, а в неполной интеграции.

1. `king_hearts.jpg`, `queen_spades.jpg`, `jack_clubs.jpg` предварительно загружаются в `courtTextures`, но `drawAtlasCourtArt()` их не использует.
2. Только туз пик в отдельной ветке реально берёт JPG; остальные фигуры рисуются canvas-символами.
3. `atlas_court_sheet.jpg` и `oct_table_master.jpg` не используются сценой.
4. Для полного набора фигур нет согласованного атласа 12 court cards.
5. Фотографическая комната и процедурный 3D-стол имеют разные перспективу и масштаб.
6. Текущий веер на 400×924 занимает чрезмерную высоту, уходит под action console и остаётся виден после возврата в лобби.
7. `setTableColor()` обращается к `feltMat`, но материал не сохраняется в это поле.

Правильный объём нового арта:

- один согласованный атлас 36/52 лиц;
- 12 полноценных В/Д/К, а не четыре образца;
- normal/roughness для сукна и дерева на high quality;
- унифицированные SVG-иконки HUD вместо части emoji;
- 3–4 визуально различимых рубашки после того, как equip действительно обновляет существующие карты.

Не нужны сейчас:

- новая комната;
- новые throwables;
- ещё один стиль стола;
- тяжёлые GLB-декорации;
- смена арт-дирекции.

## 8. UX и game feel

### Главная проблема: интерфейс сообщает правила постфактум

Игрок может выбрать нелегальную карту, отправить её серверу и получить toast. Premium UX должен показать допустимый ход до нажатия:

- нелегальные карты приглушены;
- легальные слегка приподняты;
- при защите выбирается конкретная атакующая карта;
- drag на неправильную цель возвращает карту с короткой анимацией;
- кнопки объясняют действие, а не дублируют карточный жест.

Сейчас `handleCardPlay()` отбивает первую незакрытую пару. При нескольких атаках это лишает игрока стратегического выбора.

### Визуальный state течёт между экранами

При возврате из игры очищаются `gameState` и view, но 3D-меши руки/стола не сбрасываются. Ручной прогон показал карты поверх лобби.

Нужна явная scene state machine:

```text
LOBBY_SCENE
MATCH_ENTER
DEALING
PLAYING
ROUND_RESOLVE
MATCH_RESULT
MATCH_EXIT
```

Каждый переход имеет enter/exit cleanup.

### Accessibility

Сейчас глобально задан `user-select: none`, отсутствуют focus styles, reduced motion и keyboard model. Роли различаются преимущественно цветом/emoji.

Минимум:

- WCAG AA contrast;
- `:focus-visible`;
- доступные названия и состояния кнопок;
- не полагаться только на красный/зелёный;
- `prefers-reduced-motion`;
- настройка haptics/audio;
- масштаб текста без разрушения HUD.

## 9. WebGL и производительность

Два прогона дали разные результаты:

- headless SwiftShader: renderer не создан;
- обычный Chromium: renderer работает.

Это ожидаемый класс риска для VK WebView. Ошибка — не сам факт несовместимости headless, а отсутствие продуктового fallback и failure gate.

### Что требуется

1. До создания `CardRenderer3D` проверять, что renderer существует.
2. Если WebGL недоступен — включать 2D-table fallback или показывать совместимое сообщение, а не пустой фон.
3. Visual test должен падать при:
   - отсутствии canvas;
   - `renderer === null`;
   - page/console error;
   - отсутствии карт после раздачи.
4. Ввести quality tiers:
   - low: DPR 1, без realtime shadows, минимум частиц;
   - mid: DPR 1.5, shadow 1024;
   - high: DPR 2, shadow 2048 и дополнительные материалы.
5. Измерять frame time, а не считать наличие canvas доказательством качества.

Потенциальные источники GC/jank:

- уничтожение всех мешей соперников на каждом state;
- пересоздание seat DOM через `innerHTML = ''`;
- новый interval таймера при каждом update;
- постоянный `requestAnimationFrame` для HUD-проекции;
- создание геометрий/материалов без общего pool;
- несколько отложенных bot turns.

## 10. Аудио

Процедурный WebAudio полезен как лёгкий fallback, но не создаёт материальности дорогой колоды.

Нужны:

- записанные card pickup/slide/slap/fan/collect;
- room tone отдельным каналом;
- UI clicks, countdown и result stinger;
- variation/random pitch без повторяющегося паттерна;
- master/SFX/ambience controls;
- корректный AudioContext resume после первого gesture.

Сначала карточное фоли, потом звуки помидора.

## 11. Социальная и продуктовая петля

Существующая оболочка создаёт впечатление полной live-service, но данные в основном декоративны:

- win streak и match time для story захардкожены;
- победа визуально считает награду, но сервер не делает settlement;
- `buySkinResult` и `equipSkinResult` не обработаны клиентом;
- кнопка чата показывает описание будущего чата;
- reaction server event не имеет клиентского render path;
- нет friend invite, party, MMR, history, quests и telemetry.

Порядок:

1. честная история матча и settlement;
2. reconnect;
3. быстрые реплики с moderation/rate limit;
4. приглашение друга;
5. tutorial match;
6. ranked только после достаточной concurrency;
7. live-ops после аналитики retention.

## 12. Engineering и эксплуатация

### Текущее

- 72 tracked-файла;
- около 3600 строк основного JS;
- история разработки — несколько дней;
- один Node process;
- комнаты и пользователи в RAM;
- Three.js r128, GSAP и VK Bridge загружаются с внешних CDN;
- нет `test`, lint, format, build, CI и observability scripts;
- Docker ставит только production dependencies, поэтому visual tests не доступны в image.

Это нормальный профиль прототипа и ненормальный профиль публичной игры с платежами.

### Целевое

- npm/Vite bundle с pinned dependencies и CSP;
- TypeScript или runtime schemas на network boundary;
- structured logs с match/user/request ids;
- error tracking клиента;
- metrics: active rooms, reconnect rate, action reject rate, p95 socket latency, FPS buckets;
- graceful shutdown и drain комнат;
- Redis adapter/room ownership либо осознанно один instance;
- резервные копии и миграции Postgres;
- CI: unit → protocol integration → browser smoke → bundle budget.

## 13. Новая дорожная карта

### Gate 0 — Security freeze

До прохождения gate нельзя принимать реальные платежи.

- серверная VK session;
- закрыть forged payment;
- wallet ledger в БД;
- schema validation и rate limit;
- sanitization/XSS;
- membership/host/phase guards.

**Выход:** все негативные пробы возвращают 401/403/409, баланс изменяется только ledger-транзакцией.

### Gate 1 — Correct match

- исправить первый ход;
- запретить join/addBot/restart после старта;
- ревизия состояния и idempotency действий;
- property tests колоды;
- reconnect/resume;
- один scheduler bot turn на комнату.

**Выход:** симуляция тысяч партий не нарушает инварианты; reconnect возвращает ту же руку.

### Gate 2 — Premium hand feel

- полный атлас карт;
- адресный отбой;
- legal move preview;
- object pooling и event-driven animations;
- cleanup сцен;
- фоли карт;
- low/mid/high quality;
- 2D/WebGL fallback.

**Выход:** 55+ FPS median на target Android; нет пересечений HUD на 360×800; каждая игровая операция визуально объяснима без toast.

### Gate 3 — Social product

- tutorial;
- friend invite/private room;
- быстрый чат;
- реальные match stats и share;
- progression и история;
- analytics funnel.

**Выход:** измеряются completion, rematch, reconnect и D1; социальные действия не являются заглушками.

### Gate 4 — Scale and content

- horizontal room strategy;
- ranked/season;
- smarter bots;
- cosmetics pipeline;
- live-ops;
- spectator/tournaments только при подтверждённом спросе.

## 14. Метрики приёмки

| Категория | Требование |
|---|---|
| Безопасность | 0 способов изменить wallet без подтверждённой server transaction |
| Правила | 100% обязательных rule cases + property invariants |
| Reconnect | ≥95% возвратов в матч в пределах grace window |
| Performance | median ≥55 FPS, p95 frame time без длительных GC spikes |
| Layout | 360×800, 390×844, 414×896, landscape без перекрытия playable cards |
| Cold start | интерактивное лобби <3 с на целевом 4G |
| Reliability | visual smoke падает при renderer/page error |
| Matchmaking | bot match <5 с; PvP SLA определяется реальной concurrency |
| UX | нелегальный ход блокируется до network request |
| Operations | каждый матч трассируется по match id; есть error/FPS dashboards |

## 15. Решение по графике

**Новую графическую концепцию делать не надо.**

Нужно:

1. интегрировать уже имеющиеся арты, которые сейчас не используются;
2. дорисовать полный согласованный набор лиц;
3. исправить композицию веера и lifecycle сцены;
4. добавить performance tiers;
5. заменить часть emoji на собственный UI-набор.

Если выбирать один арт-бюджет — потратить его на **полную колоду и карточные анимации**, не на новую комнату.

## 16. Итог

Самый короткий путь к воспринимаемому AAA здесь:

```text
Trust → Correctness → Reconnect → Card feel → Social loop → Scale → More content
```

Если переставить порядок и начать с новых комнат/скинов, игра станет красивее на скриншоте, но останется небезопасным прототипом. Если пройти gates последовательно, существующей арт-дирекции достаточно, чтобы стать premium-продуктом без полного визуального перезапуска.
